# User acceptance test plan

> CMS synthetic claims - not real patient or provider performance.

Acceptance scenarios for the personas in [business requirements](business_requirements.md). Each scenario maps to a check that already runs in this repository, so acceptance is re-provable on every build rather than signed off once. Actors are documented personas, not people who were interviewed.

| ID | Actor | Business scenario | Preconditions | Steps | Expected result | Automated evidence |
|---|---|---|---|---|---|---|
| UAT-01 | Payer or provider operations leader | Confirm where paid amount is concentrated before choosing a first review segment | Warehouse built for sample 1 | Open the Tableau Executive Overview, set Year to 2009, read the top 5 percent share; compare with `reports/headline_kpis.json` | Dashboard and pipeline agree; the share is labeled a share of paid amount, not cost | `tests/test_tableau_package.py::test_hyper_tieout_passes_for_every_kpi`, `tableau/validation_evidence.csv` |
| UAT-02 | Utilization management | Check setting and condition mix for a year | Warehouse built | Open Utilization & Payment; read paid amount by setting and the top condition groups | Values match the marts; unmapped, missing and invalid diagnoses are separate rows, not one bucket | `tests/test_fixture_kpis.py::test_condition_grouping_uses_cited_ccs_categories` |
| UAT-03 | Care management | Build a starting outreach list from the risk tier | Warehouse built | Open Quality & Cohorts; read paid per beneficiary and admissions per 1,000 by tier | Tiers follow the published points rule; the page says the tier is descriptive and not CMS-HCC | `tests/test_fixture_kpis.py::test_risk_tier_counts_and_boundaries`, `tests/test_tableau_package.py::test_proxy_and_review_disclaimers_are_on_their_dashboards` |
| UAT-04 | Quality monitoring | Judge whether the readmission proxy is usable | Warehouse built | Read the numerator, denominator and both exclusion counts by tier on Quality & Cohorts | Counts recount exactly from the index table; the page states it is not a certified measure | dbt `assert_readmission_denominator_matches_index`, `tests/test_fixture_kpis.py::test_readmission_proxy_index_and_exclusion_logic` |
| UAT-05 | Provider analytics | Work a provider review queue | Warehouse built | Open Provider Operations, pick the peer group, select points on the scatter, read the filtered queue and reason codes | Only providers above the peer fence with the minimum peers and claims appear; the page says a flag is not a fraud or quality finding | `tests/test_fixture_kpis.py::test_provider_review_flags_use_peer_quartiles`, `reports/provider_action_list.csv` |
| UAT-06 | Data owner | Refuse to release a metric when the load is wrong | Fixture profile | Drop a payment row from the warehouse and rerun the build | The blocking reconciliation fails and the pipeline stops | `tests/test_reconciliation.py::test_a_payment_dropped_from_the_warehouse_is_caught_by_sql_reconciliation` |
| UAT-07 | Data owner | Confirm headline numbers survive a second method | Raw files present | Run the independent pandas recomputation and compare with the marts | Money agrees to the cent, counts agree exactly | `tests/test_fixture_kpis.py::test_payment_amounts_to_the_cent`, `reports/independent_reconciliation.csv` |
| UAT-08 | Data owner | Confirm the dbt layer matches the validated SQL | Warehouse built | Run `make dbt` and read the equivalence report | Every model matches the legacy table row for row and the headline KPIs match | `reports/dbt_equivalence.csv`, `reports/dbt_kpi_equivalence.csv` |
| UAT-09 | Payer or provider operations leader | Use the Excel review offline | Workbook built | Open `excel/claims_operations_review.xlsx`, read the Reconciliation sheet, print the executive summary | Every tie says PASS; the summary prints on two readable landscape pages with the synthetic notice | `tests/test_excel.py::test_reconciliation_sheet_ties_workbook_totals_to_duckdb`, `tests/test_excel.py::test_print_settings_keep_the_executive_summary_readable` |
| UAT-10 | Data owner | Confirm nothing beneficiary-level is published | Exports and Tableau package built | Inspect the columns of every export and every Tableau extract | No beneficiary or claim identifier anywhere; an attempt to add one fails the build | `tests/test_tableau_package.py::test_no_published_extract_contains_a_beneficiary_or_claim_identifier`, `tests/test_tableau_package.py::test_extract_guard_rejects_a_beneficiary_identifier` |
| UAT-11 | Data owner | Confirm published numbers cannot drift from the marts | Tableau package built | Change an expected KPI value and rerun the tie-out | The tie-out fails and names the metric | `tests/test_tableau_package.py::test_tieout_detects_drift` |
| UAT-12 | Data owner | Confirm the README cannot drift from the pipeline | Reports generated | Edit a headline number in the README and run the drift check | The check fails and names the block | `tests/test_pipeline_e2e.py::test_readme_blocks_are_generated_and_drift_is_detected` |

## Exit criteria

All twelve scenarios pass on the fixture profile (`make fixture-all`) and on CMS sample 1 (`make all`), and GitHub Actions is green on Python 3.11 and 3.12. A failing scenario blocks release of the affected metric; informational tie-outs that differ by design never block (`tests/test_reconciliation.py::test_informational_tie_outs_never_block`).
